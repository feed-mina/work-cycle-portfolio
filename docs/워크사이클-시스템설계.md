# work-cycle — 업무 습관 통합 시스템 설계서 (v2 · Cloudflare 기준)

작성: 2026-08-20 · v2 변경: 배포를 사내 서버 → **회사 계정 Cloudflare**로, 기존 **planning-harness(기획 하네스 루프)** 기능 이관 반영

---

## 1. 요구사항 (v2 확정본)

- 도구 7종이 개별이 아닌 **하나의 하루 사이클**로 동작
- 기록은 DB에 남고, 팀원·대표님과 공유 가능
- 새 GitHub 레포 하나로 관리, 회사 계정 이메일로 Cloudflare 배포
- 기존 planning-harness에서 이관: **회의록→이슈, 마이페이지 주간/월간 스케줄, 깃 레포·Project 지정, 칸반, 시계+위젯**

**전제 확인 1 — R2는 DB가 아닙니다.** Cloudflare에서 역할 분담이 필요합니다:

| 저장소 | 역할 | 이 프로젝트에서 담는 것 |
|---|---|---|
| **D1** (서버리스 SQLite) | 관계형 DB — 조회·집계·조인 | 체크 기록, 검증 표, 회고, 스케줄, 칸반 카드, 핀 댓글 등 **모든 정형 기록** |
| **R2** (객체 스토리지) | 파일 저장 | 회의록 md 원문, 화면 리뷰용 스크린샷 이미지, **D1 정기 백업 덤프** |

즉 "DB도 Cloudflare로"의 정확한 구성은 **D1(데이터) + R2(파일·백업)** 입니다. 기존 harness가 SQLite였다면 D1도 SQLite 방언이라 스키마 이관이 거의 그대로 됩니다.

**전제 확인 2 — 보안.** 회의록·업무 기록이 외부 SaaS(Cloudflare)에 저장되는 구조이므로, 착수 전에 "회사 계정 Cloudflare에 회의록 저장" 여부를 대표님께 한 줄 확인받는 것을 게이트로 권합니다. 승인 전엔 회의록 원문 대신 제목·링크만 저장하는 모드로 시작할 수 있게 설계에 반영했습니다 (§4 meetings.body_mode).

## 2. 하나의 사이클 (변경 없음 — 시스템의 뼈대)

```
        ┌─────────────────────────── 다음날 아침에 반영 ──────────────────────────┐
        ▼                                                                       │
[08:30 읽기] → [09:30 계획] → [작업 중] → [17:30 검증] → [보고·공유] → [17:50 회고]
 ④회의록 읽기    ⑦질문 템플릿    ⑤체크리스트   ②검증 기록      ③댓글 리뷰      ⑥AI 회고
        ▲
        └ ①시계+위젯(harness 이관): 현재 시간대의 "지금 할 단계" 표시 + 미완료 알림
```

harness의 마이페이지가 이 사이클의 **홈 화면**이 됩니다: 주간/월간 스케줄 위에 사이클 단계 완료 여부가 겹쳐 보이고, 칸반 카드·GitHub 이슈가 "작업 중" 단계의 내용물이 됩니다.

## 3. 아키텍처 (Cloudflare)

```
[GitHub: work-cycle 레포] ──(push)──▶ Cloudflare Pages CI 자동 배포
                                          │
팀원 브라우저 ──▶ Cloudflare Access ──▶ Pages (화면) + Workers/Hono (API)
회사 PC 위젯 ──▶   (회사 이메일 인증)        │            │
                                        D1 (기록 DB)   R2 (회의록 원문·이미지·백업)
                                          │
                                    Workers Cron (매일 08:25 오늘의 회의록 준비,
                                                  18:10 미완료 사이클 집계, 주1 D1→R2 백업)
GitHub API ◀── Workers (harness 이관: 회의록→이슈 생성, Project/칸반 동기화)
```

**기술 선택 (v1에서 변경)**

| 항목 | v1 (사내 서버) | v2 (확정) | 비고 |
|---|---|---|---|
| 백엔드 | FastAPI(Python) | **Workers + Hono(TS)** | Cloudflare는 JS/TS 런타임. harness가 이미 웹(JS) 기반이라 이관에도 유리 |
| DB | SQLite 파일 | **D1** | 같은 SQLite 방언. 5인 규모에 충분, 무료 티어로 시작 가능 |
| 파일 | 서버 디스크 | **R2** | 이미지·md·백업. 퍼블릭 버킷 금지, Workers 경유로만 접근 |
| 인증 | 이름 드롭다운 | **Cloudflare Access** | 회사 이메일(구글) 로그인 — 코드에서 인증 구현 불필요, 팀원 초대는 Access 정책에 이메일 추가 |
| 배포 | Docker+Jenkins | **git push = 배포** | Pages CI. Jenkins 불필요 |
| 알림/스케줄 | Windows 스케줄러 | **Workers Cron + 위젯** | 08:30 회의록 모드 전환은 위젯이 API 상태를 읽어 처리 |

트레이드오프: Cloudflare 종속(락인)이 생기지만, 무료~저비용·운영 제로·회사 이메일 인증 내장이라는 이득이 5인 규모에선 압도적. D1이 한계에 오면(팀 대규모화) 같은 SQLite 스키마로 자체 서버 이전 가능.

## 4. 데이터 모델 (D1)

harness 이관 테이블 + 사이클 신규 테이블. 모두 `cycle_date`·`user_email`(Access가 주는 회사 이메일)로 묶임.

```sql
-- harness에서 이관 (기존 스키마 기준으로 맞춰 조정)
users           (email PK, name, role)
schedules       (id, user_email, date, block_type, title, start, end)   -- 주간/월간 스케줄
git_targets     (id, repo, project_no, is_default)                      -- 기본 git 대상, 일정·칸반 연결
kanban_cards    (id, user_email, quadrant, title, gh_issue_url, sort)   -- 우선순위 매트릭스
meetings        (id, date, title, body_mode, r2_key, gh_issue_url)      -- body_mode: full(R2 원문)/link_only

-- 사이클 신규
meeting_reads   (id, meeting_id, user_email, read_at)                            -- ④
checklist_items (id, section, text, sort, active)                                -- ⑤ (FeedYERIN 이관)
checks          (id, item_id, user_email, cycle_date, checked_at)                -- ⑤
ai_requests     (id, user_email, cycle_date, user_flow, keep, dont_touch,
                 done_criteria, unknowns, final_prompt, reused_from)             -- ⑦
verifications   (id, user_email, cycle_date, item, formula, method, result,
                 status)  -- status: 확인됨/불일치→수정/미확인                     -- ②
retros          (id, user_email, cycle_date, work_summary, ai_answer_md,
                 tomorrow_prompt)                                                -- ⑥
review_targets  (id, title, r2_image_key, created_by)                            -- ③
pins            (id, target_id, x_pct, y_pct, author_email, body, parent_id,
                 resolved, created_at)                                           -- ③
```

사이클 연결 고리(변경 없음): `retros.tomorrow_prompt` → 다음날 `ai_requests.reused_from` 프리필.

## 5. 화면 구성 — harness 기능이 들어갈 자리

| 화면 | 출처 | 역할 |
|---|---|---|
| 마이페이지(홈) | harness 이관 | 시계+오늘 날짜, 주간/월간 스케줄, **사이클 진행 바(오늘 6단계 중 몇 개 완료)**, 팀원별 완료 현황 |
| 회의록 | harness 이관+확장 | 목록·읽음 체크(④)·회의록→GitHub 이슈 생성(기본 git 대상 사용) |
| 칸반 | harness 이관 | 우선순위 매트릭스, GitHub Project 동기화 — "작업 중" 단계 |
| 검증 대시보드 | 신규 (②) | 검증 표 입력 + 날짜별 팀 이력, 미확인 강조 — **대표님 공유용 대표 화면** |
| 질문/회고 | 신규 (⑦⑥) | 템플릿 폼(어제 회고 프리필), 회고 저장 |
| 화면 리뷰 | 신규 (③) | R2 이미지 위 핀 댓글 |
| /api/widget/now | 신규 (①) | 위젯·상단 시계가 읽는 "지금 단계+미완료" JSON |

## 6. 레포 구조 (github.com/feed-mina 회사용 계정/work-cycle)

```
work-cycle/
├─ src/            # Workers: index.ts(Hono), routes/, db/(D1 쿼리), gh/(GitHub API)
├─ public/         # Pages 정적 화면 (harness UI 이관)
├─ widget/         # ① PC 위젯 (API만 호출)
├─ migrations/     # D1 스키마 + FeedYERIN·harness 데이터 이관 스크립트
├─ seed/           # 체크리스트 초기 항목 (태도·개발 pdf에서 추출)
├─ docs/           # 설계서, 실행 플랜, ADR
├─ wrangler.toml   # D1·R2·Cron 바인딩
└─ .gitignore      # .dev.vars(토큰), 로컬 db — 비밀·데이터 커밋 금지
```

## 7. 마일스톤

- **M0 (반나절)**: 회사 Cloudflare 계정에 Pages+D1+R2+Access 개통, "Hello 사이클 보드" 배포 → **팀원 1명이 회사 이메일로 로그인되면 완료.** (인프라 리스크를 맨 앞에서 제거)
- **M1 (1주)**: D1 스키마 + 검증 표(②) + 사이클 보드 + 체크리스트(⑤, FeedYERIN 항목 이관). → 대표님께 /dashboard 링크 공유 가능
- **M2 (2주차)**: harness 이관 — 마이페이지 스케줄(주간/월간)·시계, 회의록 읽음(④)+이슈 생성, 질문 템플릿(⑦)·회고(⑥) 사이클 연결
- **M3 (3주차~)**: 칸반+GitHub Project 동기화, PC 위젯(①), 화면 핀 댓글(③), Cron 백업
- 각 마일스톤 완료 기준은 v1과 동일: 화면 값 ↔ D1 재조회 일치 + 두 계정 동시 사용 시 기록 분리 확인

## 8. 다시 볼 지점

- 회의록 원문 저장 승인 전: `body_mode=link_only`(제목+원본 위치만)로 운영
- GitHub 토큰은 Workers Secret으로만 (레포·화면에 노출 금지 — harness의 "관리 비밀번호 대신 로그인 계정 권한" 방식 유지)
- D1 무료 티어 한도(행 수·요청 수) 도달 시 유료 전환 또는 자체 서버 이전 — 스키마는 그대로

## 착수용 첫 요청문 (⑦ 템플릿 — M0+M1용)

> work-cycle 레포의 M0~M1을 만들어줘.
> 사용자 흐름: 1. 회사 이메일로 Cloudflare Access 로그인 2. 오늘의 사이클 보드(6단계 완료 상태)가 뜬다 3. 검증 표(항목/계산식/검증방법/결과/상태)를 추가한다 4. /dashboard에서 날짜별 팀 검증 이력이 보인다.
> 지킬 것: D1이 유일한 기록 저장소, R2는 파일만. planning-harness의 기존 기능은 이 단계에서 건드리지 않는다.
> 건드리지 않을 범위: 개인용 planning-harness 레포·evol 대시보드.
> 완료 기준: 입력한 검증 값이 D1 재조회로 일치, 다른 팀원 계정에서 같은 대시보드가 보임, git push만으로 재배포됨.
